# Technical decisions

> Current scope policy: BangleSync does not query firmware/runtime identifiers or enumerate system storage. Hardware inventory is restricted to selected app/profile files, registered settings, BangleSync-owned files, and explicit import snapshots. The dated firmware/Storage notes below are historical research context only; runtime commands do not inspect those internals.

## Current implementation status (2026-11-11)

The repository now includes a physical EspruinoTools subprocess adapter. It implements discovery, connection, scoped inventory, selected-file reads/diff and backup, guarded owned-app writes, and explicit app launch/clock restore. `sync --apply` and its `device update --apply` alias can modify a physical device after the explicit confirmation and reviewed-plan-hash gates; existing-file updates also require a verified full pre-change backup. The adapter writes in chunks, verifies stage/recovery/destination bytes, and attempts recovery, but the destination rewrite is **not atomic**. Physical support is limited and has not been qualified across devices, transports, payload types, or all failure modes. Do not interpret simulator coverage as hardware evidence.

The watch testing recorded below includes scoped reads/backups and temporary app transactions. In the latest actual-CLI validation, a generated clock app was created, updated twice, and read back through `device diff --pull`; each captured snapshot matched the workspace bytes and SHA-256, and the pre-change backup independently verified. The exact test app file was erased and verified absent. The CLI `device launch` command did not complete in the latest external-CLI test (exit 1); a later `device show-clock` succeeded. Physical app launch remains unqualified in the optional-tool configuration. After the reconnect changes, three host-subprocess termination/reconnect trials and three clean disconnect/reconnect cycles passed. A separately forced reconnect test had failed before these changes. Interrupted staging was not deliberately induced on the watch. This narrow evidence does not qualify arbitrary device changes, settings writes, or power-loss recovery. Settings are not applied per key, device-side restore is absent, and `workspace import-device` is unavailable. The watch-transfer fixture remains mock-only and is not used as the adapter's transport. User-facing device operations do not query firmware or inspect low-level/system storage. During validation, unregistered settings files were initially included in presence probes; the adapter was changed to probe only explicitly catalogued filenames, and the post-fix physical inventory contained only the selected test app filename.

BangleSync's core package now has no runtime dependencies; EspruinoTools is an optional peer and is not auto-installed. Ordinary CLI/workspace commands therefore do not install BLE or native build dependencies. The physical adapter continues to support an external EspruinoTools CLI through `transport.espruinoPath`, or an optional peer present in the consumer's project. Users who separately install EspruinoTools `0.1.67` still assume that tool's legacy optional BLE/native dependency advisories; the core tarball no longer installs them by default. The consumer audit of the core package is the release gate. Platform coverage remains limited to the tested Windows setup.

## Firmware provenance and transfer qualification (2026-11-10)

### Provenance of installed identifier `2v27.62`

The upstream Espruino `RELEASE_2V27` branch resolves to release commit [`08502f84a2706a72c6ad0a525d93ec3c74f09565`](https://github.com/espruino/Espruino/commit/08502f84a2706a72c6ad0a525d93ec3c74f09565), whose commit message is `2v27 release` (2025-06-06). This is a concrete source reference for the 2v27 release line, not a demonstrated match for `2v27.62`. Upstream README describes per-commit automatic builds for certain boards, but no matching device-specific binary, build manifest, build job/artifact, board configuration, toolchain record, or firmware-image hash has been associated with `.62`. The commit is unsigned. Consequently exact source provenance, reproducible build status, image identity, and precise Storage/interpreter build versions remain unverified. `RELEASE_2V27` must not be presented as an exact match.

The release branch `src/jswrap_storage.c` documents ordinary-file `Storage.read(name, offset, length)` as a bounded read returning a string or `undefined` when the file is absent. That corroborates the API shape only; it does not establish actual behavior in the installed build or its transport path. Source: [RELEASE_2V27 Storage wrapper](https://github.com/espruino/Espruino/blob/RELEASE_2V27/src/jswrap_storage.c), [release commit](https://github.com/espruino/Espruino/commit/08502f84a2706a72c6ad0a525d93ec3c74f09565), [release-branch README/build notes](https://github.com/espruino/Espruino/blob/RELEASE_2V27/README.md).

### Watch prototype audit

`fixtures/watch-transfer.espruino` is unexecuted on hardware and exercised only in Node's VM with a mock Storage. It uses ES5-style `var`, loops, bitwise operators, regular expressions, `JSON`, `String`, and `print`; those language/API assumptions have not been tested on the exact installed firmware. The in-tree mock tests cover RFC-style Base64 byte vectors, CRC-32/IEEE known vector `123456789` = `cbf43926`, all byte values including `0xFF`, empty input, bounded 48-byte reads, final partial chunks, invalid filenames/IDs/sizes, missing input, and changed-length short reads.

The first pass determines length, then later reads transmit chunks. It detects absent/short/changing-length files, but cannot detect same-length content mutation between passes or provide an atomic snapshot; CRC only detects accidental corruption. The watch emits CRC-32, not a watch-computed SHA-256. The receiver's host-side SHA-256 is meaningful only after complete, ordered data and a valid end marker. The prototype/host envelope is not yet an integrated transport contract: frame schemas and framing must be aligned and source-derived compatibility alone is insufficient. Bounded data chunks limit payload working set, but string concatenation, JSON serialization, VM/REPL buffers, and console output copies are not measured on-device. No 256 KB RAM budget has been demonstrated. Error output itself is only best-effort if `print` or the REPL path is interrupted.

### Host protocol security and integrity

The host generator uses Node `randomUUID()` by default; explicit IDs are restricted to 1-64 ASCII letters/digits/underscore/hyphen and receiver frame metadata must match the configured transfer ID, name, type, and length. Sequence and offsets must be exact, so duplicate/reordered/missing chunks fail. Canonical Base64, decoded size, CRC-32, then per-chunk SHA-256 are checked before the sink accepts bytes. The end frame must match declared length, chunk count, and reconstructed SHA-256. Missing completion markers fail in `simulateTransfer` and `ReplFrameReceiver.finish()`. Transfer output is not complete merely because all expected bytes appeared. The resulting SHA-256 is returned by the receiver; the backup manifest records SHA-256 only after its own complete read/verification succeeds. Incomplete or unsupported entries are rejected by verification/deployment gates.

CRC-32 and SHA-256 here provide corruption detection and content identity, not authenticity: without a trusted authenticated transport/signature, an active attacker can forge frames, checksums, and hashes. A nonce/transfer ID prevents accidental cross-transfer/stale-response acceptance, not malicious replay if IDs are predictable/reused; use fresh cryptographically random IDs and bind every response to one active request. The watch-side placeholder ID is not itself a nonce generator; it must be replaced by a host-generated fresh ID. No retry/resume is supported.

### REPL isolation and transport

No robust dedicated Espruino REPL mode has been established that guarantees console text, prompts, command echo, asynchronous device messages, and transfer output cannot collide. `echo(0)` can at most address command echo; it is not proof of exclusive output. The current REPL framing parser is a simulator, not transport qualification: it cannot prove serial/BLE byte ordering, delivery, pacing, line limits, prompt behavior, timeout/reconnect semantics, or that `print` output arrives unmodified.

Minimum safeguards before supervised read-only transport testing: a reviewed adapter with exclusive/known console ownership; a fresh unpredictable transfer ID per request; strict bounded line/frame and total-length limits; explicit ASCII-safe framing and canonical decode; exact ID/name/type/length/sequence/offset binding; CRC check before sink write; incremental whole-file SHA-256; an explicit matching end marker; inactivity/deadline and disconnect handling; temporary output that is promoted only after full validation; and no retry ambiguity or write command path. A missing/ambiguous frame must fail closed.

### Decision

- **Technically credible?** The bounded ordinary-Storage reader is a plausible prototype and host algorithms pass hardware-free tests, but it is not yet a qualified, end-to-end-compatible watch protocol. Same-length mutation, RAM/stack pressure, output behavior, and exact runtime compatibility remain open.
- **Exact firmware identified?** No. `2v27.62` is not proven to map to the upstream release commit or a reproducible build/image.
- **Ready for supervised read-only testing?** No. There is no real-device transport and no evidence of REPL isolation or exact-build execution. Do not connect or upload this fixture based on these simulator results.
- **Evidence still required for the watch-side fixture:** vendor/build provenance tying `.62` to a source commit and reproducible configuration, device-specific image/hash and Storage/interpreter build details; exact-build syntax/API and byte-fidelity evidence; same-length snapshot/change strategy; measured 256 KB RAM use; and transport/REPL isolation, pacing, bounds, disconnect and completion-marker evidence. StorageFiles with `0xFF` remain unsupported for complete logical backup. This paragraph describes the fixture research at the time it was written, not the later EspruinoTools adapter or device tests. See Current implementation status above.

## Safe device updates and cache boundaries (2026-11-11)

### Storage replacement semantics

The upstream Espruino `RELEASE_2V27` Storage wrapper documents `Storage.write(name, data, offset, size)` as returning a boolean; offset zero creates or rewrites a normal file, while later offsets populate it. The reference includes an example where writing again at offset zero rewrites the file. It does not document `Storage.rename` or an atomic replace. A live read-only REPL probe on 2026-11-11 confirmed `Storage.rename`/`Storage.move` were undefined and `Storage.write`/`Storage.erase` were functions. The probe did not query firmware metadata.

A live temporary-file transaction was then exercised on the connected watch using a UUID-unique test app filename, never the active app. The old payload was 777 bytes, the new payload 1103 bytes; both contained arbitrary byte values. The adapter staged and read back the new bytes, preserved and verified a recovery copy of the old bytes, rewrote the destination using Storage.write at offset zero, read back exact new length and SHA-256, and completed cleanup. It returned the observed sequence `staging → staged → verified → committing → committed`. The test file was erased in a `finally` cleanup path, and a second run verified that `Storage.read(testName,0,1)` returned `undefined` afterward. A later interruption exercise timed out during staging rather than commit; the CLI reported a partial transfer and the exact generated stage path, and that path was erased and verified absent with a scoped read. The active test app was not touched. This validates normal write/overwrite/readback behavior and stage-timeout cleanup, not power-loss atomicity or a real mid-commit BLE interruption.

Physical writes preflight safe catalogued target, payload bytes, expected size/hash, 32 MiB limit, and canonical aligned Base64 chunk offsets before writing. New files are staged then verified before creation. Existing owned files are staged and verified; their previous bytes are also copied to a unique recovery file and verified before commit. Commit rewrites the destination with Storage.write at offset zero; exact size and SHA-256 readback is required before temporary recovery copies are erased. If commit fails, BangleSync attempts to restore the verified previous bytes; if the transport is lost, it reconnects and retries recovery. If recovery cannot be verified, the destination and retained recovery path are reported as `recovery-required`. This transaction is recoverable but not atomic: during commit, the destination may be incomplete, and interruption across process/device reset can require manual recovery from the retained file. Per-file results retain states (`pending`, `staging`, `staged`, `verified`, `committing`, `committed`, `partially-written`, `recovery-required`, `failed`); upload success alone is not reported as commit. `device update` continues to delegate to the guarded sync workflow with its plan-hash and confirmation gates.

### Diff and cache truth

`device diff` uses only names in the selected app/profile, settings registry, BangleSync ownership and explicit import snapshots. The live inventory is metadata/presence-only and has no trusted per-file content hash. The existing physical diff reads each present selected file and compares its hash with the pinned Git baseline; it is not yet a complete local-workspace comparison or persistent hash-cache implementation. `device diff --pull` stores a timestamped immutable snapshot and hashes, but those results describe the time of import only. Cached snapshot comparisons are labeled as such and are not fresh device state. A fresh read is required to establish current content. No global Storage listing or firmware/system inventory is performed.

### Failure and backup limits

Preflight rejection leaves the destination untouched. Existing-file updates stage and verify the new bytes and a recovery copy before commit; a failed commit triggers a verified restore attempt, including after reconnect. A connection loss or power loss can still interrupt both commit and rollback; in that case the recovery copy is retained and the result is `recovery-required`. A failed new-file creation can leave a partial destination and/or staging file. These operations are recoverable but not atomic. Managed backups cover selected, catalogued user-facing files and explicitly registered settings only, subject to documented StorageFile / `0xFF` limitations. They are not full-watch backups. Firmware, bootloader, OS/runtime internals, BLE stack internals, hardware drivers and other low-level system functionality are wholly outside scope and excluded before candidate inventory.

## Platform implementation update (2026-11-11)

BangleSync uses EspruinoTools in a subprocess. Physical inventory is restricted to files declared by an explicitly selected app/profile, registered settings, BangleSync ownership, or an existing import snapshot. It does not call global `Storage.list()`, sweep all BangleApps metadata as device candidates, query unselected names, or inspect firmware/runtime identifiers. Presence probes operate only on those declared user filenames. Bluetooth selectors remain in memory and are not printed; transport diagnostics suppress identifiers.

`device diff --app <id> --pull` compares only that user's selected app files against exact Git blob bytes from the pinned BangleApps commit. The import manifest stores SHA-256 hashes and a content snapshot for the selected scope. `device diff --from-import <snapshot>` repeats the local comparison without BLE; `device backup --from-import <snapshot>` materializes the cached bytes into an independent full managed-scope backup, avoiding a second watch transfer. This cache records the state observed during the import; it is not a claim that the watch remained unchanged afterward. For a fresh diff, explicitly refresh from the watch. Backups never claim device-wide/firmware coverage, and manifest SHA-256 sidecars detect accidental corruption rather than malicious replacement.

The host sync engine compares only desired/owned user files, reads only a target when a remote content hash is unavailable, and approves updates against previous content hashes. Apply requires an explicit plan hash, confirmation, ownership checks, a verified backup for updates, and read-back verification. The operation is non-atomic if BLE is lost; partial completion is reported. There is no user-facing delete path. To replace an existing app file, the guarded apply path rewrites only that exact BangleSync-owned target after explicit plan approval and a verified backup; it retains and verifies an on-watch recovery copy until new destination verification succeeds. Unknown files are never erased. Legacy deployment and logical backup APIs are simulator-only.

Read-only diffs/imports for selected apps were performed, and their selected-scope backups verified. A BangleSync-generated clock test app was installed, updated after a verified backup, and read back with a matching SHA-256. It was launched through the user API and the watch was returned with `Bangle.showClock()`. An earlier chunk-offset update failed; the partial test file was snapshotted, then repaired and reverified. BLE discovery/downloads remain intermittent, so these are narrow qualification results, not a general guarantee for arbitrary apps or settings. Firmware, bootloader, driver, BLE-stack and runtime state is not queried. Per-key settings are staged locally but not uploaded; device-side restore and Android application support remain unavailable. Behaviour modules are only installed as selected user app files and are not an OS sandbox.

The focused Node test run for scope/cache, CLI, workspace, and backup workflows passed 21 tests. ## Focused investigation (2026-11-09)

At the time of this source-only research pass, no physical watch was contacted and source inspection was read-only. Later physical testing and adapter operation are documented in the dated sections below and in Current implementation status above. The npm metadata and published tarballs were queried with npm; GitHub upstream files were consulted for source behavior. Where upstream `master` is cited, it is not treated as proof for a specific firmware release.

### EspruinoTools 0.1.67 API and embedding

- **Package:** `espruino@0.1.67`, Apache-2.0, npm `main: index.js`, `bin/espruino-cli.js`, `engines` is not declared. Its published tarball contains `index.js`, `espruino.js`, `core/`, `plugins/`, and `libs/`.
- **Declarations:** npm metadata advertises `types: ./types/index.d.ts`, but the 0.1.67 published tarball does **not** contain `types/`. The upstream current `types/index.d.ts` was separately inspected; it declares `init`, `sendFile`, `sendCode`, `expr`, `statement`, and `flash`. Because this file was from upstream `master`, its exact correspondence to the npm 0.1.67 release is unverified. The signatures overstate certainty: `expr`/`statement` type callback values as `string`, but runtime calls the callback without a value on open failure; the other APIs type callbacks as no-argument even though `sendCode` returns captured serial text.
- **Runtime exports:** the 0.1.67 `index.js` exports the same six functions. `init(callback)` synchronously runs the callback after initialization (unless already initialized, then calls callback directly). `sendFile` synchronously reads local source as UTF-8, so it is not suitable for opaque binary backup. `sendCode`, `expr`, and `statement` open and then close the serial port and invoke their callback after disconnection; they are callback-only and do not provide structured error objects or rejection semantics. Expression results are captured by a timeout-driven close sequence. These high-level APIs are code-execution/upload oriented, not a stable read-only request/response API.
- **Initialization/global state:** `index.js` evaluates package JS in the Node global context; installs shims/assignments for `$`, `navigator`, `document`, `Espruino`, and `require`; loads `libs`, `espruino.js`, `core`, and every plugin JS file in directory order; then runs queued jQuery-ready callbacks and `Espruino.init()`. It logs while loading. The global singleton and plugins mutate shared configuration/state; repeat initialization only calls the callback and does not create a separate instance. Embedding directly in the CLI risks global pollution, cross-call state and noisy logs. Isolate it behind a transport adapter (ideally a worker/process boundary) if reused; do not couple CLI business logic to its globals.

### EspruinoTools BLE transport and adapters

- **Inspected release files:** published `core/serial_node_ble.js`, `core/serial_noble.js`, and `core/serial.js`. Espruino's serial layer expects device-plugin objects (`init`, callback-based `getPorts`, `open`, `write`, `close`, optional maxWriteLength). BLE transport uses Nordic UART service UUID `6e400001-b5a3-f393-e0a9-e50e24dcca9e`, TX `...0002...`, RX `...0003...`, and a 20-byte write limit.
- **Linux DBus plugin (`serial_node_ble.js`):** disabled off Linux. Lazy-requires `node-ble`, creates a DBus session and destroys it on process exit. Discovery starts BlueZ discovery, schedules a 5-second stop, queries device UUIDs/aliases and reports devices by Nordic service UUID or Espruino-recognized name. Scan errors are logged then collapsed to `callback([], true)`. The alias lookup chain is not awaited before `getPorts` returns, so discovered records can race. A missing module marks an error but still falls through toward `bluetooth.defaultAdapter()`. Connection chains connect → GATT → service → TX/RX → notifications. Connection/service errors become unstructured `openCallback()`; write errors close but do not call the write callback. `close` does not await disconnect. This plugin is not a robust CLI boundary as-is.
- **Noble plugin (`serial_noble.js`):** Windows first attempts `noble-winrt`, then tries `@abandonware/noble`; other platforms prefer `@abandonware/noble`, then legacy `noble`. It scans for 3 seconds and times out initialization after 10 seconds. Connect/service/notification callbacks are callback-based and mostly log errors rather than return typed failures. On initial `getPorts` before Noble is initialized, it calls `callback(reportedDevices, false)` although `reportedDevices` is declared only in the later initialized branch; this path can throw `ReferenceError`. These defects warrant an adapter/wrapper and tests or bypassing the plugin.
- **Exact optional package versions inspected:**
  - `node-ble@1.13.0` (MIT; published 2025-01-19; source package depends on `dbus-next@^0.10.2`). Its package description and implementation use BlueZ over D-Bus; it is Linux-specific, not a cross-platform choice.
  - `@abandonware/noble@1.9.2-26` (MIT; published 2025-02-09; Node `>=16`; lists `darwin`, `linux`, `freebsd`, `win32`; native N-API bindings and optional `@abandonware/bluetooth-hci-socket@^0.5.3-11`). This is a more recent candidate, but package OS metadata alone does not verify actual OS hardware paths, Windows behavior, prebuild availability or Node ABI compatibility.
  - `noble-winrt@0.1.1` (MIT; last published 2018-06-25; dependencies include `chrome-native-messaging` and `noble@^1.7.0`; Windows 10 version gate and bundled `BLEServer.exe`). It is stale and introduces a separate binary/bridge; avoid selecting it for new work unless a verified platform constraint forces it.
  - EspruinoTools declares ranges `@abandonware/noble@^1.9.2-14`, `noble-winrt@^0.1.1`, and `node-ble@^1.13.0`; do not interpret those ranges as a tested platform matrix.

### BangleApps and firmware Storage behavior

- **BangleApps source inspected:** upstream `BangleApps/backup.js` (master). It separately calls `Comms.listFiles({sf:false})` and `Comms.listFiles({sf:true})`; ordinary files are read via `Comms.readFile(filename)` and StorageFiles via `Comms.readStorageFile(filename)`. It skips `.firmware`, writes StorageFiles under `storage-files/` in the ZIP, and serially awaits downloads. Its backup path converts to a ZIP `binarystring`; it has no per-file length/hash manifest or before/after inventory consistency check, and reports a failed promise rather than preserving a partial backup. Restore behavior in this file is destructive and is expressly out of scope here.
- **Firmware source inspected:** upstream `Espruino/src/jswrap_storage.c` (master; not established as the exact `2v27.62` revision). `Storage.list(undefined,{sf:false})` enumerates ordinary files and `{sf:true}` enumerates StorageFiles; `list()` includes both by default. Ordinary `Storage.read(name, offset, length)` returns a byte string, and `readArrayBuffer(name)` is available for ordinary files. `Storage.open(name,"r")` returns a `StorageFile`; use repeated bounded `read(n)` calls until `undefined`, not `Storage.read` on a StorageFile. StorageFile stores logical files across physical chunks whose suffix bytes are internal implementation details; firmware concatenates chunks in `StorageFile.read` and `getLength()` scans the file.
- **Important binary limitation:** firmware's StorageFile implementation uses erased flash value `0xFF` as end-of-file and explicitly says not to write byte `0xFF` to StorageFiles. Thus StorageFiles cannot represent arbitrary byte streams containing `0xFF` faithfully. Ordinary Storage files have byte-oriented read APIs, but wire-level preservation still needs to be proven. BangleApps backup code's `binarystring` path is not proof of arbitrary byte fidelity across BLE/CLI conversions. Do not claim byte-for-byte completeness for StorageFiles with unrestricted bytes without a verified protocol-level encoding strategy.
- **Unresolved:** exact `2v27.62` source match; source of BangleApps `Comms.readFile` / `readStorageFile` transport encodings and their binary guarantees; behavior for empty StorageFiles and filenames near firmware length limits; whether the device REPL/EspruinoTools layer can expose bounded binary reads without text conversion; and platform-specific BLE support on the selected Node versions.

### Initial recommendation (pre-qualification; superseded below)

Do not add another BLE stack now. For the next read-only milestone, build a narrow transport adapter around EspruinoTools' existing discovery/connection where possible, but isolate its global/callback model and normalize discovery, connection, disconnection, timeout and transfer errors. In parallel, evaluate `@abandonware/noble@1.9.2-26` as the likely shared adapter candidate for Windows/macOS/Linux; retain it only after OS-specific discovery/connect smoke tests and its platform/runtime matrix are verified. Do not use Linux-only `node-ble` as the cross-platform implementation or stale `noble-winrt` by default. The next milestone is read-only discovery, connection and device information only; no upload, delete, restore or deploy.

## Pre-hardware reliability review (2026-11-10)

### StorageFile losslessness finding

The inspected upstream firmware implementation (`Espruino/src/jswrap_storage.c`, not confirmed as the exact installed firmware revision) uses `0xFF` as the StorageFile end marker and documents that byte as not writable in a StorageFile. This is a storage-representation limitation, not merely a BLE/UTF-8 transport issue: once the logical StorageFile API terminates at an `0xFF`, a higher-level base64/hex transport cannot recover bytes that were never returned. A lossless read may be possible only for files whose actual logical content contains no `0xFF`, and still requires a transport-level exact-byte proof. No alternate firmware or raw-flash procedure is endorsed. StorageFiles containing `0xFF` are therefore incomplete; no encoding workaround is claimed. Ordinary Storage has byte-oriented firmware read APIs, but end-to-end transfer preservation remains unproven.

### Safety changes

- Backup now records read failures, duplicate/invalid names, per-file SHA-256 and size, performs a second device read to detect content changing during transfer, compares normalized before/after inventory, and leaves a failed manifest rather than claiming completeness.
- Independent verification checks schema, manifest status, filename safety, uniqueness, regular files, sizes, hashes, unsupported StorageFile bytes, and missing/unmanifested directory entries. A failed backup cannot pass verification or authorize deployment.
- Deployment now requires a verified backup outside the CLI workspace, verifies that backup immediately before a write, compares its manifest inventory and each device file's bytes against current device contents, requires a plan hash and explicit confirmation, rejects overwrite, rechecks that targets remain absent, verifies source bytes have not changed, and requires separate protected-file opt-in/confirmation. Partial write results are explicit and always non-atomic.
- Explicit mappings reject duplicate targets/sources and unsafe path-like filenames. Windows-reserved names are also rejected so a host backup cannot silently map to a different path.
- CLI configuration parsing no longer treats malformed JSON as an absent configuration. Hardware commands remain disabled unless `--simulate` is given; no fallback to simulated success occurs for hardware mode.

## Real-device transport qualification (2026-11-10)

### Decision: do not add a hardware transport yet

EspruinoTools remains the most practical candidate to study: its upstream repository is active (the inspected BLE plugin history has a 2026-04-21 commit), and `espruino@0.1.67` supplies serial/BLE adapters. It is **not qualified as BangleSync's binary-safe transport**. No dependency has been added and all real-device commands remain fail-closed.

- `node-ble@1.13.0` is an MIT-licensed BlueZ/D-Bus implementation, Linux-specific. It cannot supply Windows/macOS support by itself.
- EspruinoTools' Noble adapter selects `noble-winrt` on Windows before falling back to Noble, and uses Noble on macOS/Linux. `@abandonware/noble@1.9.2-26` metadata lists `darwin`, `linux`, `freebsd`, and `win32` and Node `>=16`; that is package metadata, not verified Windows 11/macOS/Linux hardware behavior or a tested support matrix. The `noble-winrt@0.1.1` path is stale. Therefore there is no established single cross-platform Node transport; supporting the three OSes may require separate backend selection and per-OS qualification.
- The EspruinoTools serial plugin interface (`getPorts/open/write/close`) is internal plugin infrastructure. Its public Node exports are oriented to init, expression/code sending and flashing, not a documented typed byte-download API. Runtime initialization loads plugins into mutable globals. `Utils.downloadFile` is an internal `Espruino.Core.Utils` helper, not a stable public adapter contract.
- The current upstream `Utils.downloadFile` reads ordinary Storage using `Storage.read`, StorageFiles using `Storage.open(...).read(384)`, and emits base64 chunks through REPL output. The 384-byte chunk size is base64-friendly, but the output has no explicit chunk sequence, declared total byte count, or end-to-end digest. The helper collects a time-delimited expression result (maximum timeout configured as 600 seconds). Its `if (s)` test also conflates an empty ordinary file with a missing value. In the current CLI path the helper returns a JavaScript binary string; writing that string through Node's default UTF-8 `writeFileSync` is not byte-safe for values above `0x7F`. This implementation is not accepted as proof of arbitrary-byte fidelity or reliable transfer completion.
- EspruinoTools' BLE plugins use the Nordic UART Service and short characteristic writes (20 bytes in the inspected DBus plugin). DBus discovery/connect/cleanup and Noble connection/disconnect paths are callback/event based and have unstructured error paths; scanning timers and the expression timeout do not amount to an end-to-end bounded transfer protocol. On 2026-11-10, its Windows Noble/WinRT path did discover and establish a real connection to `Bangle.js aeef`; a REPL identity query succeeded, but no Storage read or write was attempted. That validates connectivity only, not the transport's completeness/integrity for backup data.

A future adapter should isolate EspruinoTools or another BLE backend and use a framed read-only REPL protocol: explicit file kind/name/expected length; bounded offset reads for ordinary Storage; sequential `StorageFile.read` for StorageFiles; base64-encoded chunks with sequence number and decoded length; an explicit terminal record with chunk count and total length; strict framing/timeout handling; before/after inventories; and host-side byte count/SHA-256 verification. Empty files must be distinguished from missing files using `!==undefined` and length metadata. This protocol is a design proposal only; it has not been implemented or validated on hardware.

### Firmware source mapping

The source tree has an upstream `RELEASE_2V27` tag at commit `08502f84a2706a72c6ad0a525d93ec3c74f09565` (commit message “2v27 release”); the release-tagged Storage source blob inspected is `4f36841bf2205f7208ac566c7b36b28a2208b47f`. This identifies the **2v27 release line** associated with reported firmware `2v27.62`, but does not establish that `.62` maps byte-for-byte to this exact source commit or to a specific Bangle.js 2 build. No build manifest or physical device version was available, so the `.62` build mapping remains unresolved.

The `RELEASE_2V27` Storage source confirms:

- Ordinary files use `Storage.read(name, offset, length)` and `Storage.readArrayBuffer(name)`; the source expressly says these are for normal files, not StorageFiles. `Storage.list` distinguishes `{sf:false}` and `{sf:true}`.
- StorageFiles must be read using `Storage.open(name,"r")` and repeated bounded `read(len)` calls, not `Storage.read`. Their storage uses numbered chunks. The source explicitly says erased flash bits (`0xFF`) are used for end detection and character code 255 must not be written. `StorageFile.read` stops at the first 0xFF. Therefore logical StorageFile content containing that byte cannot be represented/retrieved as an ordinary data byte; data beyond such a marker is inaccessible through this API. Valid logical StorageFile data excluding the end marker is in principle readable, but transfer fidelity is still unproven. Raw flash contents are out of scope and cannot be called a logical backup.

## REPL framing qualification (2026-11-10)

### Release-source API findings

The upstream `RELEASE_2V27` branch points to commit `08502f84a2706a72c6ad0a525d93ec3c74f09565`; the source file `src/jswrap_storage.c` documents and implements ordinary-file `Storage.read(name, offset, length)` using `jsfReadFile`, with offset in bytes and a positive bounded length. Its comment identifies the return as a string and says it is memory-mapped/read-only; it is not itself a `Uint8Array`, and transmission as JS text still requires explicit byte-safe conversion. `Storage.readArrayBuffer(name)` calls the same file reader and converts to an ArrayBuffer, but it reads the entire file and is therefore not the incremental option. Its docs explicitly say these methods are for normal files, not StorageFiles. `Uint8Array` is defined in the same release source tree and can view/copy an ArrayBuffer.

`Storage.open` is declared in the same source as the StorageFile API, but this investigation did not establish implementation-level EOF/length behavior for the returned `File` object or find `File.getLength` implementation in the inspected Storage wrapper excerpt. Treat StorageFile incremental reads, `getLength()`, and EOF signaling as unverified until source definitions and target build behavior are confirmed. No built-in Base64 API was verified from this source pass. A custom Base64 encoder over numeric byte values is theoretically possible, but this is not a verified implementation. SHA-256 availability and an incremental hashing API on the watch were not established. **None of these release-branch observations is evidence that installed firmware `2v27.62` is built from this exact commit.**

### EspruinoTools and line protocol

The inspected upstream EspruinoTools `core/serial.js` is from `master`, not tied to a specific tools release. It receives transport buffers, converts them into text for serial handling, and parses REPL control/response behavior; transport callbacks expose chunks rather than guaranteed whole replies. The inspected Node BLE plugin documents a 20-byte TX limit and logs diagnostics separately, illustrating why application-level commands and response strings cannot be treated as atomic. This does not prove a complete Base64 response can be carried without truncation or unrelated output interleaving on any selected real transport. The actual EspruinoTools version used by a future adapter must be pinned and audited.

Host REPL simulator envelope: one line per frame, `@@BANGLESYNC/1:<transferId>:<base64(JSON-frame)>:END@@`. Newlines define envelope boundaries; arbitrary REPL echoes, prompts, and diagnostics are ignored unless a line begins with the protocol prefix. A candidate transfer ID must match both envelope and inner frame; JSON framing is followed by the existing ordered sequence, offset, chunk hash, total length, end-count, and whole-file hash checks. Malformed protocol-looking lines, stale IDs, partial lines at completion, transfer timeout, and disconnect fail closed. The envelope uses Base64 only for its structured ASCII frame and does not replace underlying chunk validation. A response is complete only after a valid end frame; no success is inferred from expression evaluation, prompt appearance, or command completion.

This is a host-side framing specification, not proof that real REPL output will delimit or isolate the marker lines. Echo suppression, prompt placement, unsolicited output, line buffering, maximum response size, BLE fragmentation/reassembly, flow control, timeouts, and disconnect detection are transport-dependent. A production adapter needs command correlation and an explicit control channel or serialized command lock; otherwise an unrelated watch print could imitate protocol text. Source evidence does not qualify that risk. The unexecuted watch-side fixture was not created because safe Base64, incremental SHA-256, and exact-build API behavior have not been established.

### Simulator status and recommendation

`src/repl-framing.js` models echoes/prompts/diagnostics, arbitrary split chunks, concatenated records, stale IDs, malformed/partial lines, disconnects, and bounded line size. `test/repl-framing.test.js` verifies only valid framed data reaches the existing reassembler and failures do not complete. The simulator cannot establish real timing, physical transport loss, or output interleaving. StorageFiles with unsupported `0xFF` remain incomplete, without raw-flash access.

**Recommendation: the REPL framing is specified sufficiently for continued host-side prototyping, but not sufficiently qualified to connect to a physical device or proceed to a supervised read-only hardware test.** Before that test, verify a pinned EspruinoTools build, exact target firmware identity, byte-encoding and checksum APIs on target, bounded StorageFile read/EOF behavior, and framing under target REPL/transport fragmentation and unsolicited output. No watch was contacted and no watch-side code was executed.

## Target-side feasibility follow-up (2026-11-10)

### Source-verified ordinary and StorageFile behavior

Further inspection of the `RELEASE_2V27` `src/jswrap_storage.c` identifies the StorageFile methods and important correction to the earlier tentative notes:

- Ordinary `Storage.read(name, offset, length)` forwards to `jsfReadFile`; its API comments define offset/length in bytes, a returned string, and `undefined` when the file is not found. A positive length bounds each read. `Storage.readArrayBuffer(name)` also calls `jsfReadFile` but requests the whole file before converting it to an ArrayBuffer, so it is not suitable for bounded incremental transfer.
- `StorageFile.read(len)` calls `jswrap_storagefile_read_internal`; the source reads at most the requested bytes in an internal 32-byte scratch buffer and advances the file object's chunk/offset state. The API documents a possibly short final String and `undefined` if already at EOF. `readLine()` is not appropriate for arbitrary binary data. `getLength()` is implemented and documented as a scan from the beginning; it determines logical length by locating byte `0xFF`.
- StorageFile's source explicitly says erased-flash `0xFF` marks end-of-file and must not be written. Consequently this API cannot distinguish a legitimate `0xFF` byte from end-of-file and cannot yield arbitrary byte values losslessly. It remains incomplete by policy.
- `Uint8Array`/`ArrayBuffer` exist in the 2v27 source tree, but the ordinary `readArrayBuffer` path is whole-file. `Storage.read` returns a String; mapping each `charCodeAt` value to its low byte is supported by the byte-string storage implementation but still needs exact-build round-trip validation before declaring hardware correctness.

The investigated Storage source can support a bounded ordinary-file prototype. That is source-level feasibility only: no exact firmware image or matching source commit metadata establishes that installed `2v27.62` corresponds to this branch/revision.

### Proposed fixture and integrity model

`fixtures/watch-transfer.espruino` is an unexecuted Espruino-style read-only prototype. It uses ordinary `Storage.read` with bounded offsets in a first pass to determine total length and a second pass to emit small chunks; it contains a local byte-to-Base64 encoder and CRC-32, requires a host-generated transfer ID, includes byte offset/length and emits start/chunk/end/error records using ASCII-only `print` output. It performs no Storage writes. Source evidence justifies the APIs and algorithms, but does not establish that every firmware build's `print`/REPL path preserves complete records, that all output is line-atomic, or that the fixture runs unchanged on `2v27.62`. It is a fixture, not a deployable or qualified watch program. No built-in Base64 or exposed incremental SHA-256 API was established; the fixture deliberately uses no watch-side cryptographic hash.

The host should validate canonical Base64, exact expected offset/length and sequence, declared total and explicit end count. Verify the sender's CRC-32 for each decoded chunk, then compute SHA-256 while writing the reconstructed file and compare a final host digest over the exact received bytes. This detects ordinary accidental frame corruption and truncation with strong checks; CRC-32 is non-cryptographic and is not an authenticity check. Host SHA-256 is a stable digest of the received backup, but without a trusted source digest it does not prove the source bytes were not already changed before transmission. Never accept a short file merely because a command returned or a prompt reappeared.

### REPL boundary strategy and limits

The inspected EspruinoTools serial layer processes transport receive buffers incrementally and contains REPL response/control handling; it does not provide a generic isolated, typed transaction response for arbitrary emitted `print` output. High-level `expr`/`sendCode` style APIs may capture text but their completion boundary is not a proof that all frames arrived, remain un-interleaved, or represent the file. A practical adapter must serialize commands, use a fresh host-generated nonce per transfer, require exact marker envelope and inner nonce, strict sequence/offset, per-frame CRC, declared length/end count and host SHA, reject duplicate/stale records, and distinguish open/close/error/timeout from a valid end. Keep unrelated output outside recognized marker records; malformed protocol-prefixed output is a hard failure. Partial lines at timeout/disconnect fail, and stale IDs cannot satisfy a new transaction. This detects many interleaving/loss cases but cannot prevent a coincidental or malicious output source from forging a valid marker; the test fixture has no authentication. Response size, line buffering, prompt behavior, BLE fragmentation, pacing, and event ordering need validation for a pinned EspruinoTools + actual transport.
